# Design notes

Why the plugin works the way it does. Code comments cite these as `D<n>`. What Wise's API actually returns, probed on a real account and the sandbox, is in [docs/wise-api.md](docs/wise-api.md).

The plugin is a provider plugin: `sync` returns records in Securo's contract 1, and Securo writes them through the same pipeline its native bank connections use, matching each record by `external_id`.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | A read-only API token is the only credential. No balance statements, no SCA, no keys. | Wise refuses statements to a personal token outside the US, CA, AU, NZ, SG and MY (403 with an SCA challenge). Signing that challenge with an uploaded RSA key was still refused on a real account, and the newer one-time-token flow doesn't know the challenge (`ott_not_found`). OAuth needs a Wise partner agreement. |
| D2 | Public plugin. No tokens, ids, names or real amounts in the repo; every fixture is made up. The sampler writes outside the repo. | Anyone can read the code. |
| D3 | Standard-library Python only, no lockfile. | Nothing to vendor or pin. |
| D4 | External-id formats: accounts `wise:<profile>:<balance>`, transactions `wise:<profile>:<activity>`, plus `:in` for the credit side of a move between balances. | Securo matches every record by its external id, so a format that changed would sync everything again beside what is already there. |
| D5 | Transactions come from the activities feed. Each moves its balance by the *balance-side* amount, which is `secondaryAmount` when present (on a send, the amount plus Wise's fee) and `primaryAmount` otherwise. `<positive>` marks money in. Amounts are parsed strictly, and a format not seen before fails the sync. | It is the one source a read-only token gets everywhere. On the real account, these amounts summed per currency equal Wise's balances exactly. A guessed amount would be wrong silently, a refused one loudly. |
| D6 | Every balance is an account, empty or hidden ones included: STANDARD balances as `checking`, Jars (SAVINGS) as `savings`. Names are "Wise USD", "Wise Business USD", "Wise Jar: Holiday (EUR)". The balance is Wise's `amount.value`, read as a decimal. | Each is money Wise holds. The profile in the name tells two USD accounts apart. Floats lose cents. |
| D7 | A conversion or Jar move (`INTERBALANCE`) is two transactions: a debit on the source and a credit on the destination. The title names the destination ("To Holiday", "To EUR"). The source is the balance in `secondaryAmount`'s currency for a conversion, or the one other balance in the same currency for a Jar move. When that isn't exactly one balance, the sync fails. | No endpoint looks these up (all 404), so the title is the only clue. Two Jars in one currency, or a Jar named like a currency, can't be told apart, and guessing would put money on the wrong account. |
| D8 | Moves between the person's own balances are described `Wise: converted EUR to USD` / `Wise: moved EUR balance to Holiday Jar`. The manifest's rule `wise-own-balances` files that prefix under Securo's built-in Transfers category. Nothing else gets the prefix. | Securo pairs a transfer's legs only on equal amounts, which a conversion's never are, so without the rule a conversion counts as spending plus income. Plugin rules can't match `provider_category`, so the description carries the signal. |
| D9 | A send stays one transaction for everything that left the balance. A same-currency fee (`secondaryAmount − primaryAmount`) goes in `raw_data.fee`. | It is one movement of the balance, and the balance must still add up. A cross-currency fee isn't comparable from the feed, and the quote that holds it is refused for some transfers. |
| D10 | Status: `COMPLETED` is posted and `IN_PROGRESS` is pending. `REQUIRES_ATTENTION` ("Waiting for you to pay", "Sending paused"), `UPCOMING` and `CANCELLED` moved no money and are left out. A transaction sent as pending that Wise then cancels is sent again as a posted 0 with "(cancelled)" appended; `state.pending` remembers what was sent as pending. An unknown status fails the sync. | Unfunded and cancelled transfers keep a send's amounts in the feed but never touch the balance. The contract has no delete, and a posted zero takes the money back out of every total. |
| D11 | A profile's history is read once to the end, continuing across syncs from Wise's own cursor. Each call stops at a 45 s budget or before Securo's 20,000-transaction cap. A cursor Wise refuses restarts the read. Once complete, a sync re-reads from the last complete read less 30 days (`since`). | Securo stops a plugin call at 60 s. The feed isn't in date order, so it can't be cut by date during the first read. The overlap lets pending activity be seen settling or cancelled. |
| D12 | A transaction's date is the UTC day of the activity's `createdOn`. | The feed gives UTC timestamps and the plugin isn't told the person's time zone. Late-evening activity west of UTC lands on the next day. |
| D13 | The client sends its own `User-Agent`, follows no redirects, caps responses at 10 MB, parses JSON numbers as decimals, and never puts the token, a query or a body in an error message. 401 → `NeedsAuth`; 403 with an SCA challenge → `NeedsAuth` saying a token can't pass it; 429 → `RateLimited`; 5xx and network failures are retried. Details Wise hides from a token (some transfers, cards) are optional. | Cloudflare in front of Wise refuses Python's default agent (error 1010). Securo shows error messages to the person, and a redirect could carry the token to a host the manifest doesn't declare. |
| D14 | The accounts name their logo by key (`institution_logo: "wise"`), and the file ships in the package. Accounts carry no institution name. | Securo serves a packaged logo itself, so showing it reaches no outside host. An institution name would replace each account's own name, and every account would read "Wise". |

## Not covered

- **Card details** (merchant category, location, the original foreign amount): every card endpoint answers 403 to a personal token, and is documented for partner OAuth only. Card payments carry the feed's amount and the merchant's name.
- **Foreign-currency card payments, refunds, cashback, interest and direct debits** haven't been seen on a real or sandbox account. D5's strict parsing means a new shape fails the sync with its format masked rather than landing wrong.
- **People without a Wise business account** can't create a token. See the README for their routes into Securo.
